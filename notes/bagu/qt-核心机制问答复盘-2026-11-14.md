## 一、首轮诊断（12 题）

### Q1｜对象模型：Q_OBJECT 到底生成了什么

- **条件**：一个 QObject 子类写了 `Q_OBJECT`、`signals`、`Q_PROPERTY`；另一个同类故意漏写 `Q_OBJECT`。
- **我的回答**：“好像帮忙生成了个什么函数，说不清楚，不确定。”
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：moc 为带 `Q_OBJECT` 的类生成 ① `staticMetaObject`（字符串表 / 方法表 / 属性表）；② 每个信号的**函数体**；③ `qt_static_metacall`（按 method index 分发）；④ `metaObject() / qt_metacast() / qt_metacall()` 重写；⑤ 属性的读写入口；⑥ `tr()` 的翻译上下文。漏写 `Q_OBJECT`：信号只有声明没有函数体，emit 时**链接错误**；字符串版 connect 运行期 `No such signal`（`metaObject()` 退化回 `QObject`）；`Q_PROPERTY` 不进元对象；`qobject_cast<T*>` 编译期 `static_assert` 失败；`tr()` 能编译但翻译上下文错误。
  - 人话：`Q_OBJECT` 是去 moc 那里“办证 + 登记”，漏了就“只有名字没有身份证”。

### Q2｜元类型：自定义 struct 跨线程传参

- **条件**：工作线程 emit 信号，参数是自定义 `struct`，接收方在主线程；对比 Qt 5 / Qt 6。
- **我的回答**：不知道。
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：Queued 连接需要把参数复制进 `QMetaCallEvent`，依赖 `QMetaType`。Qt 5 需 `Q_DECLARE_METATYPE` + `qRegisterMetaType`；Qt 6 对**编译期已知的完整类型自动注册**，队列连接通常不再需要手动注册（6.10.1 实测：普通 struct 未声明也能跨线程）。`Q_DECLARE_METATYPE` 仍用于 `QVariant`、QML、按字符串名查找、插件边界。
  - 人话：Qt 5 要先“上户口”，Qt 6 基本自动上户口。

### Q3｜信号槽：连接类型与 Auto 的判定

- **条件**：`connect` 第五参数默认；问 Auto 何时 Direct / Queued，`BlockingQueued` 何时死锁，还有哪些类型。
- **我的回答**：“主线程调用？子线程调用？不确定。”
- **判定**：⬜ 空白（没理解问题本身）
- **正确理解**：
  - 专业：`Auto` 在 **emit 时**比较“发射信号时所在线程”与“receiver 所属线程”：相同 → Direct，不同 → Queued。`BlockingQueued` 用信号量阻塞发送线程直到槽执行完；发送与接收同线程、或接收线程没有事件循环 / 已退出 → 死锁。另有 `UniqueConnection`（去重）。
  - 人话：Auto 看两边户籍；BlockingQueued 自己等自己会死锁。

### Q4｜信号槽读代码：context object 的作用

- **条件**：短命对话框 `this` 监听长命单例 `m_model`，lambda 捕获 `this`，第三参数分别传 / 不传 `this`。
- **我的回答**：不知道。
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：第三参数是 **context object**，连接在 context 销毁时自动断开，防止 lambda 在 `this` 死后访问悬空指针；不传则连接只随 sender 销毁而断开。QObject 析构时，它作为发送方的出边被断开，作为接收方的入边被清理。
  - 人话：传 `this` = “我一死，这个哨兵自动撤”；不传就等着出事。

### Q5｜事件系统：sendEvent vs postEvent

- **条件**：比较两者在同步性、返回值、事件对象所有权、线程安全上的区别。
- **我的回答**：不知道。
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：`sendEvent` 同步直接调用，返回 bool（事件是否被处理），事件对象由调用者管理（通常栈上），不能跨线程使用；`postEvent` 异步投递到 receiver 所属线程的事件队列，无返回值，事件对象必须堆分配并由事件循环 `delete`，线程安全。两者最终都经 `QCoreApplication::notify` 分发。
  - 人话：sendEvent 当面说、说完才走；postEvent 投信箱、谁收谁处理。

### Q6｜事件循环：processEvents 为什么是坏味道

- **条件**：耗时任务期间调用 `processEvents()` 让界面“暂时不卡”。
- **我的回答**：不知道。
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：它在当前调用栈里插队处理事件，导致**重入**——对象可能在嵌套处理中被删除、事件乱序、槽递归、CPU 空转。正解：耗时任务放子线程，或拆成 `QTimer` 分片。
  - 人话：“暂停手上的活去接客”，客人可能把你的活搅乱。

### Q7｜线程：QThread 两种写法

- **条件**：继承重写 `run()` vs worker + `moveToThread`；问推荐哪种、`moveToThread` 的前置条件。
- **我的回答**：“后者更灵活……QThread 不能绑定父窗口，不确定。”
- **判定**：⚠️ 半对（直觉对，术语混）
- **正确理解**：
  - 专业：继承 `run()` 适合没有事件循环的循环型任务；worker + `moveToThread` 适合事件驱动任务，可复用事件循环与信号槽，官方推荐。`moveToThread` 条件：对象无 parent、在对象当前所属线程调用、非 QWidget、目标线程未在析构。
  - 人话：最好“招人 + 调岗”，别把“科室本身”当员工用。

### Q8｜线程亲和性：run() 里 new 的对象属于哪个线程

- **条件**：`QThread::run()` 里 `new` 一个 QObject；主线程直接调用它的成员函数；跨线程信号为什么能在另一线程执行。
- **我的回答**：“亲和性？主线程，因为另外开了线程。”
- **判定**：❌ 错
- **正确理解**：
  - 专业：`run()` 里 new 的对象，亲和性属于**新线程**；主线程**直接调用**成员函数仍在主线程执行（亲和性只影响事件/信号投递，不影响函数调用）；跨线程信号 Auto → Queued → `postEvent` 到 receiver 线程 → 由其事件循环执行槽。
  - 人话：户籍决定快递送到哪，不决定你亲自跑过去干活。

### Q9｜生命周期：父子树、delete、deleteLater

- **条件**：父子对象树析构顺序；`delete` vs `deleteLater()`；信号槽里 `delete this` 的风险。
- **我的回答**：不知道。
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：`~QObject` 先发 `destroyed()`、断开连接，再递归删除子对象；`delete` 立即析构，`deleteLater()` 投递 DeferredDelete 到对象所属线程、需要事件循环处理；槽内 `delete this` 危险（信号分发可能仍访问 receiver），应使用 `deleteLater`。
  - 人话：删父连坐子；当场开除 vs 提交离职申请。

### Q10｜Model/View：自定义 model 的契约

- **条件**：自定义 `QAbstractItemModel`；插入行；`dataChanged`；`reset` vs `layoutChanged`。
- **我的回答**：不知道。
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：只读最少实现 `index() / parent() / rowCount() / columnCount() / data()`；插入必须成对 `beginInsertRows / endInsertRows`；改数据必须 `emit dataChanged(topLeft, bottomRight, roles)`；`beginResetModel` 用于整体重建（会丢选择/展开状态），结构变化可用 `layoutChanged`。
  - 人话：model 是数据、view 是显示屏、delegate 是画笔。

### Q11｜布局 / 绘制 / QSS

- **条件**：`sizeHint / sizePolicy / layout` 的关系；QSS 对自绘 QWidget 不生效的原因；`update` vs `repaint`。
- **我的回答**：不知道。
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：布局按 `sizeHint` + `minimumSizeHint` + `sizePolicy` 分配空间；自绘 QWidget 的 QSS 需要在 `paintEvent` 里用 `QStyleOption` + `QStyle::PE_Widget` 绘制，或设置 `WA_StyledBackground`；`update()` 异步合并请求，`repaint()` 同步立即绘制。
  - 人话：布局是“排座位”，QSS 是“刷漆”，自己刷墙别怪模板漆没上。

### Q12｜构建与部署

- **条件**：Qt 6 用 CMake 的最小工程；`windeployqt` 的作用；缺 `platforms/qwindows.dll` 的报错。
- **我的回答**：不知道。
- **判定**：⬜ 空白
- **正确理解**：
  - 专业：`find_package(Qt6 COMPONENTS Widgets)` + `qt_standard_project_setup()`（开启 AUTOMOC/AUTOUIC/AUTORCC）+ `qt_add_executable()` + `target_link_libraries(app PRIVATE Qt6::Widgets)`；`windeployqt` 复制 Qt DLL、平台插件、翻译；缺平台插件时报 “no Qt platform plugin could be initialized”。
  - 人话：插件目录不全，程序连“窗口”都开不出来。

## 二、口头检查（11 题，边讲边问）

### Q13｜Queued 连接，接收线程没有 exec，槽会执行吗

- **条件**：连接类型为 Queued（或 Auto 跨线程），接收线程没有 `exec()` 在跑。
- **我的回答**：“不会，因为 exec 在跑才能从 QObject 中取出事件，`QObject::event()` 分发。”
- **判定**：✅ 对（一处措辞需修）
- **正确理解**：
  - 专业：事件不存放在 QObject 里，而是排在 **receiver 所属线程的事件队列**；`exec()` 取出 → `QCoreApplication::notify` → `receiver->event()` → `QMetaCallEvent::placeMetaCall` → 槽执行。没有 exec 就没有人取，永远不执行。
  - 人话：**信箱属于线程，地址属于对象。**

### Q14｜setEnabled(false) 之后为什么看不到按钮变灰

- **条件**：按钮槽里执行 `setEnabled(false); QThread::msleep(3000); setEnabled(true);`。
- **我的回答**：“往主线程塞了绘制事件，主线程 sleep 三秒，醒来后绘制灰色事件排在恢复正常前面，灰色执行了但很快恢复。”
- **判定**：⚠️ 半对
- **正确理解**：
  - 专业（实测）：只发生一次 paint，且 `isEnabled = true`。`update()` 只标记脏区并请求重绘（UpdateRequest），paint 在真正执行时读取**当前状态**；两次请求被合并，灰色一帧都不会出现。
  - 人话：**update 记账，paint 结账，结账只看当时的状态。**

实测日志：

```text
--- 调用 setEnabled(false)
--- 主线程 sleep 300ms（事件循环停摆）
--- sleep 结束，调用 setEnabled(true)
--- 槽返回，事件循环继续
[paint] isEnabled = true  paintCount = 1
```

### Q15｜3 秒耗时活丢到子线程后，主线程在干什么

- **条件**：耗时任务在 worker 线程执行，结果通过信号回主线程显示。
- **我的回答**：“主线程分发事件给子线程，继续事件处理，等子线程处理完，这边再进行显示。”
- **判定**：⚠️ 半对
- **正确理解**：
  - 专业：每个线程有独立的事件队列与事件循环；主线程**派活**（跨线程信号 / 排队调用），不会把自己的事件分发出去；主线程继续跑自己的事件循环，不阻塞；worker 完成后 emit → Queued → 主线程队列 → 主线程槽更新界面。
  - 人话：两个前台，各管各的队列；主线程从不等人。

### Q16｜moveToThread 之后，主线程直接调用成员函数

- **条件**：worker 已 `moveToThread` 到子线程，主线程直接调用 `worker->onValue(5)`。
- **我的回答**：“直接在主线程进行，因为属于直接在主线程调用。”
- **判定**：✅ 对
- **正确理解**：
  - 专业：线程亲和性只决定事件投递目标；成员函数调用就是普通 C++ 调用，在调用者线程执行。跨线程直接调用不安全（数据竞争），应走信号槽 / 事件。
  - 人话：你能直接打电话，不代表对方安全。

### Q17｜started → work 在哪个线程执行

- **条件**：模板 `connect(thread, &QThread::started, worker, &Worker::work)`；worker 已迁到子线程。
- **我的回答**：“子线程；started 由子线程发出；信号在哪发射，槽就在哪执行。”
- **判定**：✅ 结论对 / ❌ 后半句口诀错
- **正确理解**：
  - 专业：`started` 在新线程发出，worker 户籍也在新线程 → Auto 同线程 → Direct → 在 emit 处执行。**“信号在哪发射，槽就在哪执行”只对 Direct 成立**；Queued 时槽在 receiver 所属线程执行，与发射处无关。
  - 人话：Auto 看两边户籍，不要看信号从哪发。

### Q18｜为什么 worker 不能有 parent

- **条件**：`Worker *worker = new Worker(this); worker->moveToThread(&thread);`。
- **我的回答**：“相当于绑定在这个线程里了，后面又移到另一个线程，好像冲突，不能进行绑定。”
- **判定**：⚠️ 方向对
- **正确理解**：
  - 专业：parent 关系要求“同线程 + 同生共死”；`moveToThread` 会连同子对象一起迁移，带 parent 的对象迁移会破坏父子树，因此被拒绝并打印 `QObject::moveToThread: Cannot move objects with a parent`，对象留在原线程。后果：`started → work` 变成 Queued，耗时活被排回主线程执行，界面照样卡——**线程白开**。
  - 人话：办了“父子证”就不能单方面调岗。

### Q19｜finished → deleteLater vs finished → delete worker

- **条件**：子线程 `quit()` 后 `finished` 发出，worker 无 parent。
- **我的回答**：“子线程还在……前者在子线程执行 deleteLater；后者直接删主线程里的对象。”
- **判定**：❌ 错
- **正确理解**：
  - 专业：`quit()` → `exec()` 返回 → `run()` 返回 → 发出 `finished`（此时子线程事件循环已退出）。两种写法**都在子线程执行**（Auto 同线程 → Direct）。区别是时机：`deleteLater` 投递删除请求，线程收尾 / 循环空闲时安全销毁；`delete` 当场析构，可能在信号分发中、或有挂起事件 / 定时器时出问题。
  - 人话：离职申请 vs 当场开除。

### Q20｜漏掉 finished → deleteLater 会怎样

- **条件**：worker 无 parent；只 connect 了 `done → quit`；反复开关 100 次。
- **我的回答**：“严重的内存泄漏，因为 connect 本身语法没问题。”
- **判定**：✅ 对
- **正确理解**：
  - 专业：每次泄漏一个 worker（及其连接、QThreadData、句柄）；不崩溃、不报错，内存缓慢增长；靠反复开关压测 + 内存曲线发现。另外 `quit` 后应有 `wait()` 或 `finished → deleteLater`，否则可能打印 `QThread: Destroyed while thread is still running`。
  - 人话：不报错的错，最难查。

### Q21｜moc 生成的 pinged 函数体里是什么

- **条件**：头文件只声明 `signals: void pinged(int);` 且有 `Q_OBJECT`；打开 moc 生成的 `moc_*.cpp`。
- **我的回答**：“漏 Q_OBJECT 就不会去这个类检索信号与槽、不会生成这个函数；moc 帮忙生成了一个信号调度的入口函数。”
- **判定**：✅ 概括对
- **正确理解**：
  - 专业：实际生成如下代码。它只负责“上报”，不负责“通知谁”；谁接收由 `connect` 登记在 sender 的连接表里，`activate` 查表后按连接类型执行槽。

```cpp
// moc_tracedobject_trace01_metacall.cpp（Qt 6.10.1 生成）
void TracedObject::pinged(int _t1)
{
    QMetaObject::activate<void>(this, &staticMetaObject, 0, nullptr, _t1);
}
```

  - 人话：moc 写“喊话”，connect 写“点名册”。

### Q22｜同一个信号连两个槽 / 同一个槽连两次

- **条件**：同一信号 connect 两个不同槽；同一槽 connect 两次；emit 一次。
- **我的回答**：“是的，绑定顺序，算一次。”
- **判定**：前半 ✅ / 后半 ❌
- **正确理解**：
  - 专业：两个不同槽都执行，顺序为 connect 先后（同线程）；同一槽连两次会**执行两次**（connect 是追加而非设置）；去重用 `Qt::UniqueConnection`（仅成员函数版 connect 有效，lambda / 普通函数不支持）。receiver 销毁时连接自动断开。
  - 人话：名单上签两次名，就被叫两次。常见 bug：在会被反复调用的 init 函数里 connect，导致连接累积，点一次执行 N 次。

### Q23｜Model 改了数据但不通知，界面会怎样

- **条件**：自定义 model 修改了内部数据，但没有 `emit dataChanged`；问 View 会不会自己定时问 Model。
- **我的回答**：⏳ 待答
- **参考答案**：
  - 专业：View 不会轮询，只等通知。改数据必须 `emit dataChanged(topLeft, bottomRight, roles)`；插入 / 删除走 `begin/endInsertRows` 等成对接口；不通知则界面保持旧显示，直到因其他原因重绘才可能更新。
  - 人话：显示屏是“等通知的”，不是“主动查岗的”。

## 三、4 个思维习惯问题（比 API 更重要）

1. **把“谁在跑”和“信号在哪发射”绑死** → Q17 口诀错、Q19 线程判断错。Auto 的真实规则是“比较发射线程与 receiver 所属线程”。
2. **把事件当成对象自己持有的东西** → Q13 措辞。事件在线程队列里。
3. **以为“延后”意味着中间状态会执行** → Q14。中间状态会被合并 / 跳过。
4. **生命周期与删除时机概念弱** → Q19。这类错误不报错、不崩溃，最难查。

## 附录 A｜四条核心链路（速查）

### 1. 信号槽

```text
signals 声明
  → moc 生成信号函数体（内部调用 QMetaObject::activate）
  → connect 在 sender 的连接表里登记 receiver / 槽 / 连接类型
  → emit = 调该函数 → activate 查表
  → Direct：emit 线程直接调槽
     Queued：打包 QMetaCallEvent → postEvent 到 receiver 线程 → 其事件循环执行
     Auto：emit 时比较两边线程（同 Direct / 异 Queued）
```

### 2. 事件循环与绘制

```text
main → QApplication::exec() → QEventLoop::exec → 取事件
  → QCoreApplication::notify → receiver->event() → 具体 handler
update() → 标记脏区 + UpdateRequest → 事件循环 → paintAndFlush
  → beginPaint → 背景/QSS → paintEvent → endPaint → 刷屏
repaint() → 同步立即绘制
```

### 3. 线程

```text
QThread::start() → 新线程 → run()（默认 exec() 事件循环）
moveToThread：改亲和性（连同子对象），要求无 parent
跨线程 emit → Auto → Queued → receiver 线程事件循环执行
主线程直接调用 worker 函数 → 仍在主线程执行（亲和性不管函数调用）
```

### 4. 生命周期

```text
new QObject(parent) → 加入 parent 的 children
delete parent → 发 destroyed → 断连接 → 递归删除子对象
deleteLater → 投递 DeferredDelete 到对象所属线程 → 事件循环处理时删除
receiver 析构 → 它的入边连接被自动清理
```

## 附录 B｜真实错误对照表（本机实测）

| 错误消息 | 阶段 | 原因 | 修复 |
| :-- | :-- | :-- | :-- |
| `undefined reference to 'Bad::changed(int)'` | 链接 | 漏 `Q_OBJECT`，moc 没生成信号函数体 | 加 `Q_OBJECT` 并重新构建 |
| `QObject::connect: No such signal QObject::changed(int)` | 运行 | 漏 `Q_OBJECT`，`metaObject()` 退化为 QObject | 加 `Q_OBJECT` |
| `qobject_cast requires the type to have a Q_OBJECT macro` | 编译 | 目标类没有 `Q_OBJECT` | 加 `Q_OBJECT` |
| `QObject::moveToThread: Cannot move objects with a parent` | 运行 | 对象有 parent | 无 parent 再 move |
| `QObject: Cannot create children for a parent that is in a different thread` | 运行 | 跨线程创建子对象 | 在对象所属线程创建 |
| `QThread: Destroyed while thread is still running` | 运行 | 线程未结束就析构 QThread | `quit()` + `wait()`，或 `finished → deleteLater` |
| `QWidget: Must construct a QApplication before a QWidget` | 运行 | 静态 / 全局 QWidget 早于 QApplication | 延迟创建 |
| `This application failed to start because no Qt platform plugin could be initialized` | 启动 | 缺 `platforms/qwindows.dll` | `windeployqt` |
| `QBackingStore::endPaint() called with active painter` | 运行 | paintEvent 中 QPainter 未析构 | 用作用域限制 QPainter |
| `Cannot queue arguments of type 'X'` | 运行 | Qt 5 元类型未注册（Qt 6 大多自动） | `Q_DECLARE_METATYPE` / `qRegisterMetaType` |
